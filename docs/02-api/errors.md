# Errors and Exceptions

## Exception categories

### Validation exceptions

Generated by Form Requests when input does not satisfy endpoint rules. Expected HTTP status: `422`.

### Authorization exceptions

Raised when authentication or policy checks fail. Expected statuses: `401` or `403` depending on whether the user is authenticated.

### BusinessRuleException

Used for valid requests that violate a business invariant or lifecycle rule.

Examples:

- Starting a project that is not `Planned`.
- Holding a project that is not `InProgress`.
- Completing a task that is not `InProgress`.
- Completing a project while incomplete tasks remain.

These conflicts use `409 Conflict`.

### Unexpected exceptions

Unexpected failures should be handled by Laravel's global exception pipeline and logged. API clients should receive a stable error envelope rather than internal implementation details in production.

## Error design goals

1. Stable status code.
2. Machine-readable error type/code where the project defines one.
3. Human-readable message.
4. Validation details when relevant.
5. No stack trace or sensitive infrastructure detail in production.
